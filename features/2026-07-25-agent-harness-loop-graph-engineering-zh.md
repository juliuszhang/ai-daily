# 智能体运行框架工程、循环工程与图式工程

> **原文标题**：Agent Harness Engineering vs. Loop Engineering vs. Graph Engineering  
> **作者**：[@beamnxw](https://x.com/beamnxw)  
> **原文发布日期**：2026 年 7 月 25 日  
> **原文链接**：[x.com/beamnxw/status/2081022966645535079](https://x.com/beamnxw/status/2081022966645535079)  
> **分类**：AI Agent、智能体架构、软件工程  
> **说明**：本文为非官方中文翻译。为避免歧义，文中的 **Harness** 统一译为“智能体运行框架”，也可理解为智能体的外壳、支架或运行底座。原文部分句子略显生硬，译文在不改变技术含义的前提下进行了中文表达整理。

*一份实用指南，解释人们经常混为一谈的三层智能体架构。*

产生混淆是可以理解的：这三个概念都围绕同一个模型展开，都会影响系统可靠性，而且都可能包含“循环”。

但它们并不是同义词。它们分别对应不同的工程决策。当智能体不再只是演示 Notebook，而开始接触文件、API、客户或生产代码时，区分它们就变得非常重要。

## 30 秒看懂区别

- **智能体运行框架工程（Harness Engineering）**：构建模型周围的整套运行机制。
- **循环工程（Loop Engineering）**：设计反复执行、获取反馈和改进的工作周期。
- **图式工程（Graph Engineering）**：把工作流拓扑明确表示出来，包括节点、分支、汇合、状态转换与受控循环。

最清晰的心智模型是：

> **环境 → 反馈 → 流程**

原文配图中的对比可以概括为：

| 维度 | 智能体运行框架 | 循环工程 | 图式工程 |
|---|---|---|---|
| 核心关注点 | 运行与操作能力 | 迭代推进和反馈 | 显式控制流程 |
| 核心对象 | 模型包装层或运行时 | 有边界、可重复的循环 | 由步骤组成的有向图 |
| 常见组件 | 工具、记忆、沙箱、中间件、权限、轨迹 | 触发器、目标、行动、证据、反馈、停止规则 | 节点、边、共享状态、分支、汇合、中断、循环 |
| 解决的问题 | “模型无法安全地完成工作” | “智能体过早停止，或反复做低质量工作” | “工作流难以理解或控制” |
| 最适合 | 通用智能体平台或专用运行时 | 需要通过验证逐步改进的开放式任务 | 有明确决策点的复杂多步骤流程 |
| 主要风险 | 运行时臃肿、不透明 | 无限重试、Token 浪费、奖励投机 | 过度设计、流程路径脆弱 |

## 为什么这些术语突然变得重要

一个裸语言模型本身无法维护项目状态、运行测试套件、查看浏览器、执行审批规则，也不能重新启动失败的任务。

这些能力都来自模型所处的运行环境。

随着智能体软件逐渐成熟，一套相对标准的工程技术栈正在形成：

1. 最底层是**智能体运行框架**，也就是实际运行模型的代码和环境；
2. 其上是各种**循环**，负责重复执行任务和进行质量检查；
3. 最后是**图式工作流**，把整个流程的结构化路径表示出来。

这些称呼目前仍未完全标准化。

“智能体运行框架”正在逐渐形成较具体的定义；“循环工程”则是 2026 年开始在从业者之间流行的新说法。至于“图式工程”，不必把它理解成某个学术领域——它只是把智能体工作流构建成显式有向图或状态机的过程。

这种实用层面的区分，可以防止流行术语掩盖真正需要解决的设计问题。

## 一、智能体运行框架工程

按照 LangChain 的说法：

> **智能体 = 模型 + Harness。**

Harness 是模型之外的代码、配置和执行逻辑。实际系统中通常包括：

- 系统提示词；
- 工具定义；
- 记忆；
- 文件系统；
- 沙箱；
- 模型路由；
- 任务交接；
- 中间件钩子；
- 上下文压缩；
- 权限；
- 日志；
- 验证接口。

OpenAI Agents SDK 从运行时角度描述了相同的核心机制：Runner 调用模型、执行工具调用、处理任务交接、携带状态，并且只有在任务到达真正的终止条件时才停止。

“Harness”这个词的价值，在于它把注意力从对模型能力的盲目崇拜中移开。

两个团队即使使用相同的基础模型，也可能得到完全不同的结果：

- 一个团队为模型提供清晰的工具、稳定的工作区、受约束的权限和可观察的状态；
- 另一个团队只给模型一个模糊提示词，再套上一层不可靠的 API 封装。

模型的智能程度也许差不多，但它们的**工作条件完全不同**。

### 一个成熟的运行框架通常包含什么

- **上下文注入**：指令、检索到的事实、对话状态、技能和任务专用策略。
- **行动接口**：API、浏览器、Shell、代码解释器、数据库和 MCP 工具。
- **持久化能力**：文件、检查点、会话、进度日志、Git 历史与长期记忆。
- **执行控制**：超时、重试、预算、模型路由、子智能体生成与审批关卡。
- **安全与治理**：权限、隔离、白名单、密钥处理与人工授权。
- **可观测性**：执行轨迹、工具输入输出、状态转换、成本、延迟与评估结果。

模型处在一个更大的系统中，这套系统负责上下文、控制、行动、持久化和验证。

你可以把模型从架构图里删掉。剩下的一切，大概率都属于 Harness：

- 工具；
- 数据访问；
- 状态存储；
- 沙箱；
- 中间件；
- 评估器；
- 重试策略；
- 用户界面。

原文配图展示的完整 Harness 还包含：

1. 规划与任务拆解；
2. 后端和文件系统；
3. 上下文工程；
4. 隔离、并行或异步运行的子智能体；
5. 短期与长期记忆；
6. 可复用技能；
7. 隔离执行沙箱；
8. 人工审批；
9. 自定义函数、MCP Server 和内置工具。

这些能力最终服务于任意支持工具调用的语言模型。

### Harness 工程什么时候最有价值

对于长期运行的任务，Harness 尤其重要。

Anthropic 在多会话编码任务中发现，仅仅压缩上下文并不足以维持可靠进度。他们采用的不是一个“更好的提示词”，而是一套更完善的工作环境：

- 创建初始化程序；
- 保存进度文件；
- 保留 Git 历史；
- 坚持增量式工作；
- 让每个新上下文都能理解之前完成了什么、接下来还要做什么。

这是一套围绕智能体建立起来的、更可靠的工作系统。

当智能体出现以下问题时，应优先考虑 Harness 工程：

- 缺少完成任务所需的能力；
- 中断后无法干净恢复；
- 丢失状态；
- 拥有过宽的访问权限；
- 无法审计；
- 在不同环境中的表现不一致。

## 二、循环工程

每一个使用工具的智能体，内部都已经存在一个基础小循环：

1. 调用模型；
2. 查看模型输出；
3. 执行工具；
4. 把工具观察结果重新输入模型；
5. 重复以上步骤，直到返回最终答案。

当开发者开始有意识地在这个基础行为外部构建或叠加新的周期时，就进入了 OpenAI 所称的“循环工程”。

例如：

### 验证循环

智能体先创建一个产物，然后：

1. 运行确定性检查或评估器；
2. 接收明确反馈；
3. 只有发现有证据支持的错误时才重试。

### 事件驱动循环

当出现以下事件时唤醒智能体：

- 到达预定时间；
- 收到 Webhook；
- 出现新文档；
- 检测到新数据。

### 改进循环

分析执行轨迹与失败案例，然后：

1. 修改指令或工具；
2. 测试新版本；
3. 判断它是否真正优于旧版本。

LangChain 在 2026 年提出的框架将其描述为“**一组相互叠加的循环**”，而不是某个神奇的 `while` 语句。

### 一个设计良好的循环由什么组成

- **触发器**：什么会启动下一轮？用户请求、计划任务、测试失败、新数据或评估反馈。
- **目标**：要到达什么具体状态，而不是模糊地要求“继续改进”。
- **状态和记忆**：下一轮需要知道什么，同时避免重新播放全部历史。
- **行动策略**：智能体可以修改什么、调用什么、委派什么，以及允许花费多少资源。
- **证据**：测试、Schema 校验、引用、Diff、指标或人工评审。
- **反馈**：用简洁、可执行的方式说明证据为什么没有通过。
- **停止规则**：成功、达到预算上限、超时、不可恢复错误或升级给人工处理。

验证循环是在基础智能体循环外部，再套上一层外部评估器和明确的通过条件。

> **不要围绕“信心”循环，要围绕“证据”循环。**

“智能体说自己完成了”不是停止条件。

真正的停止条件应该是：

- 测试通过；
- 链接可以正常访问；
- Schema 校验成功；
- 审查者批准。

### 为什么循环工程不只是提示词工程

提示词规定模型在**单次调用中**应该做什么。

循环则规定系统在模型调用结束后做什么：

> 如何观察结果、选择反馈、决定是否继续、持久化进度，以及何时终止。

提示词质量当然仍然重要，但循环可以把一次性指令变成一个受管理的过程。

它的主要代价是成本和延迟。每增加一个评估器、审查者或重试过程，就会增加一次模型调用或工具执行。

Anthropic 的总体建议是：

> 选择能够解决问题的最简单架构；只有当性能收益足以证明其价值时，才增加智能体复杂度。

同样的原则也适用于循环：只有当任务失败造成的损失高于验证成本时，才值得加入复杂循环。

## 三、图式工程

图式工程提出的是另一个问题：

> 不只是“智能体要做什么”，而是“接下来允许哪个组件运行”。

在图式工作流中：

- 步骤表示为**节点**；
- 允许发生的转换表示为**边**。

边可以表达：

- 顺序执行；
- 条件分支；
- 并行扇出；
- 任务汇合；
- 循环；
- 人工中断。

状态会沿着图移动，而图的拓扑结构让系统能够检查和约束预期的控制流。

LangGraph 将自己定位为一种面向长期、有状态智能体的底层编排基础设施，重点提供：

- 持久化执行；
- 状态管理；
- 人在回路控制；
- 对智能体行为的显式控制。

Microsoft AutoGen 的文档给出了很直接的建议：如果需要以下能力，就应该使用图：

- 精确控制智能体执行顺序；
- 根据不同结果选择不同的后续步骤；
- 确定性的分支；
- 包含循环的复杂多步骤流程。

### 图式工程真正需要决定什么

- **节点边界**：哪些工作应由确定性函数、LLM 调用、专业智能体或人工评审完成。
- **状态结构**：每个节点可以读取或更新什么，并行更新如何合并。
- **路由条件**：什么证据会让任务向前、向后、横向移动，或升级处理。
- **并发方式**：哪些任务可以并行，哪些必须汇合，哪些共享资源需要协调。
- **循环与出口**：什么位置允许重试、最多重试几次、怎样保证循环安全。
- **持久化**：在哪里创建检查点，中断后如何恢复执行。

这里的图式工程指的是**基于图的执行流程工程**，并不是知识图谱工程。

二者的区别是：

- 知识图谱表达数据中的实体及其关系；
- 工作流图表达控制流程和状态转换。

### 什么时候值得使用图

如果流程包含以下内容，图会非常有价值：

- 有意义的条件分支；
- 并行工作；
- 审批流程；
- 故障恢复路径；
- 多个专业智能体。

如果任务只是“给一个智能体三个工具，然后让它工作”，图的价值就比较有限。

图可以改善调试能力，但也可能过早固化假设。如果模型需要动态创造计划，而开发者强迫它把所有可能路径预先画进图里，系统反而可能变得更加脆弱。

## 三层架构如何协同工作

假设我们要构建一个“研究并发布行业简报”的智能体。

### Harness 提供基础能力

- 浏览器；
- 搜索工具；
- 文档工作区；
- 引用存储；
- 模型路由；
- 密钥管理；
- 权限控制；
- 执行轨迹日志；
- 审批界面。

### Graph 规定任务路径

任务按照以下流程推进：

> 范围界定 → 并行研究 → 来源筛选 → 综合整理 → 起草 → 法务审查 → 发布

并且在正式发布前设置人工审批关卡。

### Loops 负责重复验证和改进

- 当信息覆盖不足时，重新检索来源；
- 当引用验证失败时，将草稿退回修改；
- 当市场发生变化时，按照计划重新生成和刷新内容。

三者之间是嵌套关系：

> **图运行在 Harness 之内；一个或多个循环运行在图的节点中；Harness 为循环提供状态、工具与评估器。**

这些类别会发生重叠，是因为软件层本来就会重叠。但当系统失败时，每一层仍然对应不同的解决杠杆。

### 根据故障症状选择工程层

| 症状 | 优先检查 | 可能的解决办法 |
|---|---|---|
| 智能体无法安全访问正确的数据或工具 | Harness | 改进工具契约、权限、沙箱和上下文注入 |
| 智能体跨会话忘记任务进度 | Harness | 持久化状态、检查点、进度产物和上下文压缩 |
| 第一次结果往往接近正确，但不够稳定 | Loop | 外部评估器、确定性测试、明确反馈和有限重试 |
| 智能体成功后仍继续工作，或尚未证明成功就停止 | Loop | 基于证据的终止状态和预算感知停止规则 |
| 多个专业智能体必须按照受控顺序运行 | Graph | 显式节点、边、路由条件与汇合点 |
| 多步骤流程发生故障时难以定位 | Graph + Harness | 将带状态的执行轨迹与图节点、状态转换对齐 |
| 工作流变化太快，不适合固定图结构 | 更简单的 Harness | 保持由模型动态控制，推迟将流程正式图式化 |

## 薄弱智能体架构背后的昂贵错误

### 1. 在理解任务之前就建立复杂图

一些团队还没有观察到一个有能力的智能体会怎样解决任务，就先把业务流程转换成数十个节点。

更好的方法是：

1. 先用简单 Harness 运行；
2. 收集真实执行轨迹；
3. 观察哪些路径比较稳定；
4. 再将稳定路径正式固化成图。

### 2. 让同一个模型同时负责创作和评分

自我审查有一定帮助，但写作者和评分者可能共享相同的盲区。

应该优先使用：

- 确定性检查；
- 独立的审查上下文；
- 对高影响操作要求人工批准。

### 3. 把“继续尝试”当成循环规格

无限重试循环会持续泄漏成本。

每个循环都必须具备：

- 可衡量的目标；
- 新的验证证据；
- 最大尝试次数；
- 明确的升级处理路径。

### 4. 把 Harness 当成什么都往里塞的垃圾场

更多工具和记忆并不一定更好：

- 工具太多会增加选择错误；
- 上下文太嘈杂会增加模型困惑；
- 权限太宽会增加安全风险。

### 5. 把编排问题归咎于模型

模型无法可靠弥补以下缺陷：

- 过期状态；
- 含糊的工具 Schema；
- 损坏的 API；
- 缺失的退出条件。

应该改进真正拥有这个故障的工程层，而不是笼统地指责模型。

## 面向生产环境的设计清单

### Harness

- 工具是否足够聚焦，并有清晰文档和可观测性？
- 状态是否持久化？
- 是否遵循最小权限原则？
- 运维人员能否暂停、检查和恢复一次运行？

### Loop

- 什么证据能够证明任务成功？
- 失败时会返回什么反馈？
- 最多允许重试多少次？
- 预算耗尽时应该发生什么？

### Graph

- 哪些路径必须是确定性的？
- 哪些任务可以并行运行？
- 哪些状态需要共享？
- 人工审批关卡和故障恢复路径在哪里？

### Evaluation

- 团队能否重放真实执行轨迹？
- 能否比较不同版本？
- 能否把性能提升归因于某项具体修改，而不是依靠直觉？

### Operations

生产环境中是否监控了：

- 成本；
- 延迟；
- 失败率；
- 人工干预率；
- 任务级成功率？

## 最简单的记忆方法

- **Harness 工程**：构建模型周围的系统，让模型真正具备运行和工作的能力。
- **循环工程**：让工作过程可以迭代、验证和恢复。
- **图式工程**：让复杂执行路径变得显式且可控。

三者无法互相替代。

如果 Harness 丢失了状态，再漂亮的工作流图也没有用。

如果没有证据和停止规则，再优秀的 Harness 也只会让循环不断烧钱。

如果分支、并发和审批全部埋在临时代码里，即使精心设计了循环，系统仍然很难维护和操作。

只有把这三层放在一起设计，并明确每一层究竟要解决什么问题，才能构建出真正可靠的智能体系统。
