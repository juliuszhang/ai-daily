*我们为更先进的模型删掉了 Claude Code 系统提示词中超过 80% 的内容。下面介绍如何把从中获得的经验，应用到 Claude Code 以及你自己的智能体上下文工程中。*

我之前写过，应该如何为新一代 Claude 5 模型设计提示词，以及如何通过迭代协作，逐渐明确自己究竟想构建什么。相关内容可参阅 [Claude Fable 实战指南](https://claude.com/blog/a-field-guide-to-claude-fable-finding-your-unknowns)。

但当你向 Claude 发送消息时，提示词只是 Claude 所获得上下文中的一小部分。上下文中的大量内容来自系统提示词、Skills、`CLAUDE.md` 文件、记忆以及其他来源。

我们把组装这些信息的工作称为[上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。无论你是在使用 Claude Code，还是在构建自己的智能体，它都会对最终结果产生重大影响。

与单次提示词不同，上下文通常会在许多不同请求中被重复使用，因此不可能针对每一个请求都写得非常具体。当你甚至不知道用户接下来可能提出什么问题时，应该如何为 Claude 编写这种通用提示和指导？

随着 Claude 自身能力不断进化，这件事可能出乎意料地困难。最近，我们发现新一代 Claude 模型所需要的提示方式发生了显著变化。

对于 Claude Opus 5、Claude Fable 5 等模型，我们删掉了 Claude Code 系统提示词中超过 **80%** 的内容，而编码评估结果没有出现可测量的下降。

下面是我们在为这类新模型设计提示时获得的经验，以及你应如何利用这些经验更新自己的上下文工程。我们已经把这些最佳实践加入 `claude doctor`；你可以在 Claude Code 中使用 `/doctor`，帮助调整 Skills 和 `CLAUDE.md` 文件的规模。

## 解除 Claude 的束缚

总体来看，我们发现，无论在系统提示词中，还是在 `CLAUDE.md` 文件和 Skills 中，我们都对 Claude Code 施加了过多约束。

例如，在阅读团队内部使用 Claude Code 的执行记录时，我们会在同一个请求中看到多条互相冲突的信息：系统提示词可能要求“在适当情况下保留文档”，某项 Skill 却要求“不要添加注释”，而用户自己的请求又可能提出第三种要求。

原文配图把这种情况表示为一个由多层信息组装而成的上下文：

| 上下文来源 | 示例要求 |
|---|---|
| 系统提示词 | “在适当情况下保留文档” |
| Skills | “不要添加注释” |
| 用户请求 | “只要让它像旧版本一样能用” |

> 这些只是说明性示例，并非任何真实系统提示、Skill 或用户请求的逐字引用。它们最终进入同一个上下文，Claude 必须读取全部内容并协调其中的冲突。

通常，Claude 能理解用户意图并得出正确答案，但在决定具体应该怎么做之前，它必须花费更多推理来处理这些重叠甚至相互冲突的信息。

这些限制过去确实有必要，可以帮助旧模型避开最坏情况。但我们后来发现，其中很多限制现在都可以删除，让模型根据周围上下文和自身判断作出决定。

此外，Claude Code 如今拥有的工具也比过去多得多。以前，Claude 主要依赖 `CLAUDE.md` 获取记忆、信息与指导；现在则有记忆、Artifacts 和 Skills，可以用新的方式跨会话加载和共享上下文。

## 过去与现在

过去的很多上下文工程最佳实践，如今已经逐渐变成了不再适用的“神话”：

| 过去 | 现在 |
|---|---|
| 给 Claude 大量规则 | 让 Claude 运用判断力 |
| 给 Claude 大量示例 | 设计好接口 |
| 一开始就放入全部信息 | 使用渐进式披露 |
| 重复同一套说明 | 使用简洁的工具描述 |
| 把记忆写进 `CLAUDE.md` | 使用自动记忆 |
| 使用简单规格说明 | 提供丰富的参考资料 |

### 过去：给 Claude 规则

### 现在：让 Claude 运用判断力

Claude Code 刚推出时，我们需要确保 Claude 能够避开删除文件等最坏情况。这意味着我们会给出非常强硬的指导，即使这些规则并非在所有情况下都正确。

例如，旧系统提示词曾这样写：

> 在代码中，默认不要写注释。绝不要写多段 Docstring 或多行注释块——最多只能写一行简短注释。除非用户明确要求，否则不要创建规划、决策或分析文档；应根据对话上下文工作，而不是依赖中间文件。

但对于某些请求，这些规则显然是不对的。用户可能对文档有自己的偏好，或者某段高度复杂的代码确实需要多行注释块。

尽管如此，对于旧模型来说，如果缺少这些护栏，Claude 写出的注释在很多情况下会不正确，所以我们不得不接受这种取舍。

新模型拥有更好的判断力，即使没有显式规则，也能妥善处理这些决定。因此，新系统提示词只需要说：

> 编写与周围代码风格一致的代码：匹配现有代码的注释密度、命名方式和惯用写法。

与其规定“永远不要写什么”，不如要求模型观察当前代码库，并作出与局部上下文相匹配的判断。

### 过去：给 Claude 示例

### 现在：设计接口

以前，工具使用的首要原则是向 Claude 提供大量使用示例。

但对于最新模型，我们发现示例实际上可能把 Claude 限制在某个固定的探索空间中。

与其堆积示例，不如认真设计工具、脚本和文件本身：Claude 可以使用哪些参数？这些参数能否更清晰、更富有表达力？

例如，在 Todo 工具中，仅仅把 `status` 定义为以下枚举：

- `pending`
- `in_progress`
- `completed`

就已经能提示 Claude 应该如何使用它。再加上一条“同一时间只能有一个任务处于 `in_progress` 状态”的约束，就足以定义我们希望得到的行为。

原文配图对比了 TodoWrite 的新旧设计：

- 旧版工具描述约有 **9,100 个字符**，包含“什么时候使用”、完整示例等大量文字；
- 新版只保留简短的接口说明、状态枚举，以及“同一时间只能有一个进行中任务”这条关键约束。

换句话说，应该让接口本身传达使用方式，而不是依赖冗长的解释和示例。

### 过去：把所有信息都放在最前面

### 现在：使用渐进式披露

由于 Claude Code 主要面向编码任务，我们以前会在系统提示词中放入大量有关代码审查和验证的详细信息。

这些信息并非每次任务都需要，但一旦用到，又非常关键。

此后，Claude Code 越来越擅长使用“渐进式披露”：在正确的时间加载正确的上下文。例如，我们已经把验证和代码审查说明移动到各自独立的 Skills 中，让 Claude Code 只在需要时选择性调用。

渐进式披露并不只适用于 Skills，也适用于工具。

有些工具采用“延迟加载”：智能体在真正使用之前，必须先通过 `ToolSearch` 搜索完整定义。这样一来，我们可以提供更多工具——例如 Task 工具——而不必让它们在尚未使用时就占据上下文窗口。

你也可以把相同思路应用到自己的 `CLAUDE.md` 和 `SKILL.md` 文件中。

一个常见误区是：应该把遇到过的每一项实践全部收录进一个中央文件，否则 Claude 就找不到它们。

更好的做法是[建立一棵可以在适当时机加载的文件树](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code)。

### 过去：重复自己

### 现在：使用简洁的工具描述

早期 Claude 模型有时需要同一条指令被重复多次，也可能比起上下文窗口开头的指令，更容易听从末尾的指令。

因此，我们过去会在主系统提示词中提到某个工具，同时又在工具描述中重复相同的使用说明。

现在我们发现，可以删除这些重复内容。工具使用方法应该放在工具自己的描述中，而不是在系统提示词里再写一遍。

### 过去：把记忆存进 `CLAUDE.md`

### 现在：使用自动记忆

过去，我们会鼓励用户把内容保存到 Claude 的记忆中，例如使用 `#` 快捷键自动写入 `CLAUDE.md`。

现在，Claude 会自动保存与你以及当前工作相关的记忆，不再需要把 `CLAUDE.md` 同时当作手动记忆仓库。

### 过去：使用简单规格说明

### 现在：提供丰富的参考资料

在计划模式中，Claude Code 长期依赖包含计划的 Markdown 文件。将计划保存为文件，可以让 Claude 在之后需要时重新引用。

类似地，在代码库中保存规格说明，也是支持 Claude 处理长期项目的一项常见最佳实践。

但我们发现，Claude 现在可以处理越来越复杂、越来越丰富的参考资料。

除了简单 Markdown 文件，Claude 还可以引用由新 Artifacts 功能创建的 HTML 产物。

你也可以直接把代码作为参考。规格说明可以是一套详细测试，也可以是另一个代码库中的函数，让 Claude 把它移植到当前项目。

Rubric（评价量表）也是一种参考资料。它可以表达你在特定领域的品味，例如“什么样的 API 设计才算好”。Claude 可以结合[动态工作流](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code)，启动使用这些 Rubric 的验证智能体，不断尝试并检查结果是否符合要求。

## 如何把这些原则应用到你的上下文中

把前面的经验组合起来后，我们应该怎样组织自己的上下文？

原文配图将上下文窗口表示为多个信息切片：

1. 你的提示词；
2. References：通过 `@` 引用的文件、规格说明、Mockup、代码库和 Artifacts；
3. 系统提示词；
4. `CLAUDE.md` 文件；
5. Skills；
6. Memory。

> 用户当前输入的提示词，只是整个上下文窗口中的一个切片；图中各部分大小仅为示意。

### System Prompt

系统提示词与产品上下文高度绑定。它告诉 Claude：自己正在什么产品中运行，以及正在执行什么工作。

如果你使用的是 Claude Code，一般不会修改它的系统提示词。但如果你在构建自己的 Agent Harness，这里值得投入大量时间。

### `CLAUDE.md`

让 `CLAUDE.md` 保持轻量：简要描述仓库的用途，把大多数 Token 用在代码库中特有、容易踩坑的地方。

例如，你的团队可能规定，所有类型都必须集中放在一个单体文件中，其他位置不能定义类型。这类仓库特有规则就适合写入 `CLAUDE.md`。

不要写那些 Claude 查看文件系统或仓库后自然就能知道的“显而易见”的内容。

还应大量使用渐进式披露。例如，如果你有多项独特的工作验证要求，可以创建一个验证 Skill，再从 `CLAUDE.md` 中引用它。

### Skills

可以把 Skills 看成轻量级指南，让 Claude 在需要时找到相关信息。

除非涉及非常重要的领域，否则不要把 Skill 约束得过于严格。

对于较长的 Skill，应尽可能使用渐进式披露：把它拆成多个文件，让不同内容分别按需加载。

最有价值的 Skills，通常编码了特定的观点、知识或最佳实践，而且这些内容是你本人、你的团队或产品所特有的。

### References

你可以通过 `@` 提及文件，把它们加入参考资料。References 能让 Claude 在当前计划中查询更深入的信息。

参考资料可能包括：

- 规格说明文件；
- Mockup；
- 完整代码库；
- HTML Artifacts；
- 测试套件；
- 可供移植的现有实现。

一般来说，应优先选择代码形式的文件，因为代码能够用 Claude 非常熟悉的语言，提供清晰、高保真的说明。

例如，一个设计的 HTML Mockup，通常会比文字描述或截图产生更好的结果。

## 尝试做减法

你的系统提示词、Skills 和 `CLAUDE.md` 文件，可能都需要像我们一样进行简化。

我们推出了一个新命令 `claude doctor`，可以帮助你自动完成这项工作；在 Claude Code 中可使用 `/doctor` 检查并调整 Skills 与 `CLAUDE.md` 的规模。
